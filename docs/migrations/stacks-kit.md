# Stacks Kit migration: behavior contract

Part 1 freezes behavior before changing dependencies. No production implementation, manifest, lockfile, or Bitcoin bond vector changes belong in this part. Models run through their existing consumer runners; no models runner is introduced.

## Contract

The inputs and literal expected wire bytes and observable results below form the migration contract. Later parts may adapt tests, drivers and SDK-specific setup to Kit, provided the same inputs produce the same bytes and results. Whole test files are not frozen. Keep recorded fixture answers separate from the production-facing drivers. A driver must call production entry points, without reimplementing derivation, signing, encoding, fee calculation, validation, mapping, or proposal verification.

The vectors were captured against installed stacks.js: transactions 7.5.0; common, network and encryption 7.0.2; stacking 7.0.5; connect 8.2.7. Each JSON file is a known-answer artifact, not an expectation computed at test runtime. Bigints are represented as decimal strings in JSON. Hex is compared in full, including prefixes, signature recovery bytes, memo padding, post conditions and payload discriminants. JSON formatting and object property order do not affect assertions; serialized bytes still pin protocol ordering. Protocol fixtures do not store stacks.js transaction, authorization, Clarity-value or post-condition objects. The cache-persistence fixture deliberately pins the exact existing SuperJSON storage string, including its stored Clarity fields and type metadata, because old user data must still load. Clarity JSON and printed representations are pinned as observable output formats.

Initial tests were run with empty expected artifacts to demonstrate failure, then captured once against the installed dependencies. Ordinary test runs read these artifacts. The committed specs read these JSON artifacts and compare literal results, without a snapshot update path. A mismatch is a compatibility decision, not permission to regenerate the contract.

## Boundary inventory

- Account paths distinguish Leather address indices from Ledger hardened account indices. Vectors pin compressed keys, descriptors, ordered multisig and mainnet, testnet and custom-chain address behavior.
- SIP argument builders and decoding pin Clarity bytes, JSON and representation, nested optionals, tuples, lists, buffers, Unicode and large integers. Memo vectors cover the 34-byte boundary with ASCII and multibyte input.
- Transaction generation and SIP-10 transfer builders pin unsigned and signed hex, IDs, nonce and fee precision, sponsored auth, sequential and non-sequential multisig, and payload and signature-size estimates. Default and Clarity 6 deployments use the unversioned payload; an explicit Clarity 2 deployment is versioned.
- Post conditions cover STX, fungible and non-fungible assets, staking and PoX, comparator codes, standard and contract principals. PoX builders also pin origin principals and allow/deny/originator modes.
- Message signatures, Ledger VRS/RSV layout, nonce replacement and a real extension-signed proposal cover signing boundaries and rejection of tampered inputs.
- Services pin Hiro request bodies and decoded results, BNS responses, fee bounds and fallback behavior, sBTC withdrawal calldata, vendor SDK argument order and yield read-only arguments. Queries pin payload and multisig dimensions in cache keys. State and extension consumers pin persisted descriptors and network data.
- Web and test-app PoX-5 builders independently pin complete calldata and post-condition bytes. Wallet vectors pin provider selection, rejection, revocation and contract requests. Extension mnemonic vectors decrypt fixed salted and legacy ciphertext, including cached encryption keys, wrong passwords and tampering.

No vector requires live services, funds or physical hardware. Network, wallet-provider, native and Ledger plumbing are mocked at external boundaries. The mnemonic worker boundary returns a recorded Argon2 result computed with the installed bundled WASM and production parameters. Only the entropy source is fixed for encryption; encryption, decryption and legacy re-encryption remain real. Their ciphertext bytes are compared literally. All cryptographic inputs are public test material.

## Mnemonic cryptographic format

The extension first stretches the password with Argon2id (version 19, one lane, 44 iterations, 32768 KiB memory, 48 output bytes). Its salt is the UTF-8 text of the stored 32-character hex salt, not the 16 decoded bytes. The resulting 96-character hex string is used as the password for stacks.js mnemonic encryption. Legacy unsalted extension records skip this Argon2 layer and use the original password directly.

The installed stacks.js encryptMnemonic converts BIP-39 words to entropy, then uses PBKDF2-HMAC-SHA512 with a fresh 16-byte salt and 100000 iterations to derive 48 bytes: AES key [0,16), MAC key [16,32), IV [32,48). Encryption is AES-128-CBC with PKCS#7 padding. Authentication is HMAC-SHA256 over salt || ciphertext. The stored byte layout is salt[16] || MAC[32] || ciphertext; the IV is derived rather than stored. The extension stores an additional, separate Argon2 salt alongside the hex encoding of these bytes.

The vectors use public test password vector-password and sixteen 0x07 bytes as the inner salt. Injecting this salt also fixes the derived IV: salted IV ab05f6f33f97d3dd7fe27105fbf6f88d, legacy IV c0de62b5d4e0b625e05846a34184d907. There is no independent IV parameter in the installed stacks.js API. The driver fixes the Node crypto.randomBytes entropy source and does not replace the KDF, cipher or MAC. The twelve-word test mnemonic has 16 entropy bytes and a 32-byte padded ciphertext, yielding an 80-byte record. Wrong passwords and modified ciphertext are rejected.

## Complete value inventory

[stacks-kit-migration/inventory.json](../../stacks-kit-migration/inventory.json) records source files, lines, SDK symbols, value owners, destinations and named test proofs. Entries group import sites by source file; the values array records individual runtime references, including SDK instance methods. Shared protocol contracts are reused where consumers pass the same wire value. Additional entries cover storage migrations and indirect consumers without SDK imports. Test drivers are inventoried too.

Run `node stacks-kit-migration/check-coverage.mjs` to check the inventory against the source. The maintainer-supplied checker is committed unchanged at [check-coverage.mjs](../../stacks-kit-migration/check-coverage.mjs). Its `--draft` output helps identify new sites; retain stable entry IDs, fill the flow and proof, and document removed IDs under dropped. Keep this inventory complete in every migration part.

Stored-data proofs load fixed legacy localStorage vault keys, salted and unsalted ciphertext, session encryption keys, extension software/Ledger descriptors through both migrations, mobile persist-root keychains through fingerprint migrations and secure-store lookup, numeric network IDs/subnets, selected wallet IDs, policy IDs, backend raw transaction payloads and Ledger handoffs. Mnemonic encrypt/decrypt functions remain real. Later Kit implementations must decrypt these same fixed blobs with the same passwords and recover the exact mnemonic; do not replace or regenerate the blobs.
